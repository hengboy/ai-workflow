## Workflow

Planning produces frozen `spec.md` and `plan.md`; plan-to-tasks produces immutable task documents. Coding implements direct changes without planning artifacts and planned work as split tasks or an approved unsplit frozen plan, with TDD, and creates no workflow runtime artifact other than the single implementation record at `<project>/.ai-workflow/plans/<planId>/implementation.yaml`, which holds `plan_id` with `status: in-progress` and an ISO 8601 `started_at` in the UTC+08:00 timezone before the first implementation step and after the final merge and owned cleanup becomes `status: completed` with an ISO 8601 `completed_at` in the UTC+08:00 timezone and the final commit SHA, except that a workspace root prefix delivery keeps the same record `in-progress` with `root_tasks_commit` until finalization; it is the only permitted run record.

- Requests are classified before work starts: a small requirement, feature adjustment or defect fix with clear, bounded intent is implemented directly without Planning or the dual-axis review, while a new feature, unclear or contested requirements, or a public-interface, persistent-format, cross-module, cross-stack, migration, compatibility or contract change runs Planning and keeps that review gate. A planned change without a frozen plan is planned first and then handed off: the planning session never starts implementation, a plan declaring at least one non-root participating repository routes to a new session at the workspace root that invokes plan-to-tasks and then runs `ai-workflow workspace distribute --plan <directory>` before implementation, and an ordinary or root-only plan tells the user to start a new session and invoke the coding skill.
- Coding must create one project-local temporary worktree under `<project>/.worktrees/<name>` before implementation; all implementation and validation happen inside that single worktree. Git Operator materializes the project's entire gitignored state into the worktree, excluding the `.worktrees/` container, so `.ai-workflow/plans/` stays visible and single-source at the project root while the project contract, MEMORY, navigation and notes arrive with the worktree through Git.
- A split plan's execution order is frozen at split time as `tasks/execution-order.yaml`: the ordered list of non-empty parallel phases that covers every task exactly once, with every dependency in a strictly earlier phase and no overlapping normalized write-scope paths inside one phase (directory containment included). Plan-to-tasks previews the phases with the critical path and writes the file after the task triplets and their pair records; `ai-workflow plan validate --plan <directory>` reports `execution_order` and fails on a missing or invalid order. Coding treats the file as the only schedule for a split plan: phases run in file order, every task of a phase is dispatched concurrently inside the single worktree with test work before implementation in each task, and each task's write scope is committed serially through Git Operator one commit at a time before advancing; a missing or invalid order stops the run before execution, with no serial fallback and no recomputation from `depends_on`. The schedule is machine-readable and has no `.zh.md` or `.i18n.yaml` sibling, and pre-existing task sets without it fail validation by design with no migration.
- A git-submodule workspace root delivers one cross-repository plan: the root freezes the single `spec.md`/`plan.md` pair whose `workspace_repos` declaration and `workspace.yaml` manifest assign every task to exactly one repository in a repository-level delivery order. Declared `.gitmodules` submodule paths are excluded from the root's navigation discovery and validation, and a pre-existing workspace navigation is refreshed only with `ai-workflow context rebuild --project <root> --write`. `ai-workflow workspace distribute --plan <directory>` writes each participating repository's self-contained slice and refuses divergences before writing, while `ai-workflow workspace status --plan <directory>` validates the workspace manifest before reporting `valid`, reports each repository's slice, implementation-record and delivery-commit state, a `workspace_root_entry` with `record`, `tasks_delivered` and a nullable `delivery_commit`, and an `order` and `next_repository` that follow the frozen `tasks/execution-order.yaml` repository first-appearance order including pending root tasks, all without writing. A workspace plan that declares at least one non-root participating repository must be split by plan-to-tasks before implementation, and completing that split runs `ai-workflow workspace distribute --plan <directory>` after the task triplets, their pair records and `workspace.yaml` are written and `ai-workflow plan validate --plan <directory>` passes; a workspace plan whose `workspace_repos` declares only the reserved `workspace` root entry may be implemented unsplit. After all slices complete, verify each recorded delivery commit read-only and pin each affected submodule in the workspace worktree with `git update-index --cacheinfo 160000,<sha>,<path>`, staging only authorized pointer paths and workspace-root files. The workspace root owns the cross-repository decision note, each repository owns its own delivered-facts note, and cross-repository references stay plain plan-ID text. Planning routes a cross-repository workspace plan to a new session at the workspace root that invokes plan-to-tasks; a child record counts as delivered only when its `record` is `completed`, its slice is `present`, its `plan_id` matches and its `delivery_commit` is a full commit SHA, and `ready_for_finalization` combines every such child with the root `tasks_delivered`, so the root Git Operator verifies every delivery commit with a read-only `git cat-file -e <sha>^{commit}` existence check before any index mutation and pins it. The root's own tasks are delivered as an optional `root_tasks_commit` in the same root `implementation.yaml`, which stays `in-progress` until finalization, so the workflow keeps one record with only `in-progress` and `completed`, and an already-running correct root finalization session executes directly instead of reopening itself. Planning keeps the reserved `workspace` root a dependency-free `prefix` delivered separately from finalization, requires cross-repository acceptance criteria to name their owning repository with exact bounded read-only source checks, never checks out a child automatically, and keeps root owner notes separate from child delivered facts.
- Parent workspace coding orchestration is activated only for a frozen plan that declares at least one participating non-root repository matched to the current root's `.gitmodules`; an ordinary plan, a project with `.gitmodules` running a non-participating plan, and a root-only workspace plan keep the ordinary direct, mechanical, unsplit or split route unchanged. The one primary parent Coding session invokes `plan-to-tasks` as an approved preparation procedure that returns control to that same session, distributes the slices, then dispatches native leaves itself with no nested splitter, coordinator, remote session or child host process. Each active repository owns exactly one run-owned worktree at `<source-root>/.worktrees/<planId>` on branch `ai-workflow/<planId>`, and the original parent `tasks/execution-order.yaml` stays the only global schedule: a phase's independent tasks run concurrently, the whole phase is awaited and verified before its scoped task commits are written serially, and a repository's per-repository delivery review and gate complete before a dependent repository advances. Each repository's single `implementation.yaml` is written only through the filesystem-only `ai-workflow workspace checkpoint --plan <directory> --repo <name>` command after Git evidence; it accepts exactly one `start`, `task`, `reviewed`, `delivered` or `finalized` JSON event on stdin, rejects unknown fields, wrong types, a wrong plan or repository, unauthorized task IDs, contradictory duplicates, invalid transitions and malformed full SHAs before writing, is idempotent for identical repeats, and leaves the prior record byte-unchanged on refusal; the record keeps only `in-progress` and `completed` and adds an `execution` anchor, per-task `task_checkpoints` (`kind: commit` with a full SHA or `kind: no-change` with the exact HEAD) and a purpose-scoped `reviewed_commit`. Finalization runs a separate finalization review after every child and the root prefix are delivered and is executed directly by the already-running correct root session. Automatic resume is limited to a clean, fully checkpointed phase boundary or a verified repository delivery boundary, while a dirty partial phase, a commit-without-checkpoint gap, unknown future-phase progress, an uncertain review result, a contradictory record or unrelated target drift stops with a bounded support or recovery request; the CLI, real-Git and content tests cover the delivered scope, but the three-host native parent-session acceptance is not fully demonstrated and remains an explicitly reported gap, never converting unavailable authentication or trust into a pass.

- Adopted projects run the shared native synchronization preflight once when a planning, coding or plan-to-tasks skill session starts, storing the complete result in the host runtime cache keyed by the actual root outside the project; every native SessionStart, UserPromptSubmit and PreToolUse event is then served from that stored result with zero source requests, a missing or unreadable stored check allows with a visible no-check context and no freshness claim, and the next skill start atomically replaces the stored result. It patches their managed workflow instruction files from the fixed upstream source and is a narrow instruction-maintenance exception that writes only the actual project root or coding worktree, performs no Git and no product edit, and never claims freshness for a warning or unverified result; it keeps its exact sync-actor and contract-read exemptions, and the manual `ai-workflow sync` command stays a fresh, cache-independent check that never replaces the stored gate decision.

## Host role agents

- Installed role agents are native to each host: Codex uses TOML with `model`/`model_reasoning_effort`, Claude uses Markdown with `allowed-tools`, and OpenCode uses Markdown with `mode: subagent` and ordered `permissions` rules. The role's declared tools remain the single source, and only the primary orchestrator dispatches subagents.

## Project contract and Agent Notes

- Explicitly read `.ai-workflow/AGENTS.md`; its workflow rules apply to the entire project and every participating agent.
- Notes governance has one source: `.ai-workflow/notes/README.md`, reached through `.ai-workflow/notes/AGENTS.md`. Read those files before maintaining relevant notes within the task's authorized scope.
- This file records current standards (how), while notes record why. Keep them consistent in the same change.
- Navigation JSON is authoritative; regenerate and validate its Markdown view when navigation changes.
