# Agent Note: Review boundaries and repair

Status: implemented

English | [中文](2026-10-14-review-boundaries-and-repair.zh.md)

## Problem

The shipped workflow left review activation and closure under-determined. The project contract described a dual-axis review but kept an undefined larger or high-risk trigger, and `coding` still asked the user to choose between selected repairs and repairing all findings before merge. Planning ran the Spec Review after obtaining approval and could require renewed approval after an in-scope error. No boundary allowed a targeted recheck of one implicated axis after an aggregate repair, the review roles prohibited any second review including a finding recheck, and Git Operator had no accepted-source-HEAD comparison before a non-fast-forward merge. Execution Status could read as an acceptance verdict, and an unfulfilled acceptance criterion, a cited required-standard violation or unavailable required evidence had no stated blocker semantics. These gaps made review triggers non-deterministic, forced a routine selection prompt, and let closure evidence be inferred from a successful checkpoint or a `done` status.

## Decision

- The project contract `templates/project/AGENTS.md` and its tracked mirror `.ai-workflow/AGENTS.md` gain a `## Review policy` section, and MEMORY, README and this record describe the same policy: the change class is the only routine review trigger.
- Direct and Mechanical changes dispatch neither review axis, Planning dispatches only the Spec Review and never the Standards Review, and plan-to-tasks dispatches neither; an ordinary planned implementation, split or unsplit, runs one simultaneous full Spec Review and Standards Review batch after implementation and its required checks and before integration.
- A child-participating workspace keeps a per-repository delivery review for each repository delivery plus an independent finalization review, and a zero-task root has no artificial root-delivery review; there is no per-task, per-phase or per-commit trigger and no undefined larger or high-risk trigger beyond the change class.
- Planning clarifies business intent, drafts both languages in memory, runs one full Spec Review, repairs an in-scope error automatically with at most one affected-finding targeted recheck, and only then presents the complete final confirmation; no plan directory, `spec.md`, digest or task file exists before approval, and a material user change after that review starts a new planning boundary and plan ID instead of reusing stale evidence.
- The primary aggregates both axes' findings and automatically delegates one aggregate repair for evidenced defects inside the settled or frozen acceptance and existing write scopes without asking which findings to fix; Test authors required test changes first, and the boundary permits at most one aggregate repair and one targeted recheck batch that dispatches only the affected axes, both simultaneously when both are affected, carrying the original finding labels, the repair diff and fresh evidence.
- An unfulfilled AC, a cited required-standard violation or missing required evidence is a blocker and unavailable or failing required evidence stays blocking; warnings are advisory, carry a reasoned disposition and never mask a blocker. Demonstrably unsupported or duplicate findings also require reasoned dispositions and must not be silently dropped. A business or acceptance change, scope expansion, REQ/AC change or delivered-child edit stops at a bounded decision, new-plan or support request instead of an unauthorized edit.
- Execution Status and a review Verdict stay separate: `done` means execution completed and never substitutes for Verdict PASS; freeze or integration requires complete assigned acceptance evidence with no unresolved blocker, and an unresolved blocker or an unavailable recheck stops as `blocked` or `failed` with no second repair or review loop.
- Before non-fast-forward integration the primary supplies the exact accepted source HEAD, repository, worktree, purpose, base and target plus the review and check evidence; Git Operator alone compares the actual clean source HEAD with that accepted HEAD and refuses drift before merge, and the resulting delivery merge SHA is recorded independently and need not equal the source HEAD.
- A workspace `reviewed_commit` is written once only after repairs, checks, rechecks and closure are accepted, stays purpose-scoped and is never reused for another purpose or a changed HEAD; CLI checkpoint success proves only a record transition, not a review PASS or Git equality.
- The policy is shipped in `templates/project/AGENTS.md`, `templates/skills/planning/SKILL.md`, `templates/skills/coding/SKILL.md`, `templates/skills/coding/references/workspace.md`, `templates/skills/plan-to-tasks/SKILL.md`, `templates/agents/spec-review.md`, `templates/agents/standards-review.md` and `templates/agents/git-operator.md`, and guarded by `tests/behavior/review-policy.test.ts` plus the replaced conflicting assertions in `tests/behavior/planning-content.test.ts`.

## Alternatives considered

- **Keep the undefined larger or high-risk review trigger.** Declined: a non-deterministic trigger means the same change can be reviewed or not, while the change class already provides a deterministic boundary.
- **Keep the routine selected-versus-all repair choice.** Declined: asking which findings to fix delays an in-scope repair the acceptance and write scopes already authorize, and the requested handling is automatic without a selection prompt.
- **Allow a second full review or an unbounded repair loop.** Declined: one aggregate repair and one affected-axis recheck keep each boundary bounded, and an unresolved blocker must stop rather than loop.
- **Treat a successful checkpoint or a `done` status as acceptance.** Declined: a record transition proves no semantic verdict, so acceptance evidence and the clean source HEAD are required separately.
- **Equate the delivery merge SHA with the reviewed source HEAD.** Declined: a non-fast-forward merge legitimately produces a different delivery SHA, so the two are recorded as separate evidence.

- The Step 1 regression also ran the behavior/install batch as 23 files with 281 passing checks at exit 0 and the scoped project-sync batch as 5 files with 68 passing checks at exit 0; both are static shipped-content and compatibility guards, not live behavior.
- The Step 2 fixture trace exercised the policy inside disposable fixtures under `<coding-worktree>/tests/.review-policy-smoke/`: a Spec-only boundary and a both-axes boundary each ran one simultaneous full pair, one automatic local repair without a selection prompt and one targeted recheck; the Spec-only case rechecked only Spec, and the both-axes case rechecked Spec and Standards in one simultaneous batch. Real native primary dispatch, Test commands and Git Operator comparisons were performed, while the seeds, requirement texts and acceptance wording were synthetic case data, and no central transcript or runtime receipt was created. Git Operator removed the owned fixtures before the documentation commit.
- The same trace covered the bounded gate and scope cases: an unresolved Test-gate failure withheld acceptance and integration with no repair loop, and a proposed out-of-scope file was classified as a bounded scope decision rather than granted, with no file edited and Git confirming its absence. In the Git cases Git Operator compared the accepted clean source HEAD with the actual candidate HEAD and refused a drift before any checkout or merge, while an accepted clean source HEAD `778abe50f857d054ed28af7d6b1cdfa75f2eb152` produced the distinct non-fast-forward delivery merge `00e8c9596d824527b819e560381caf82cbfa88cf`, whose delivery SHA differs from the source HEAD.
- The trace demonstrates at least one actual available host: the OpenCode native primary ran these bounded ordinary review, repair and gate cases. Claude Code and Codex were not exercised, no real HOME role files were refreshed, and the existing three-host native coverage gap stays an explicit limitation rather than a claimed pass; a Planning user confirmation and a child-participating workspace session were not run in these smokes and are covered only by static regression tests.
- Four related active notes keep their independent decisions and rationale: [Change routing](./2026-09-22-change-routing.md) owns classification, [The Planning and coding session boundary](./2026-09-23-planning-coding-session-boundary.md) owns the Planning-to-Coding handoff, [Automatic implementation commit](./2026-10-14-automatic-implementation-commit.md) owns the automatic local commit, and [Parent workspace coding orchestration](../feature/2026-10-09-workspace-coding-orchestration.md) owns parent workspace execution.
