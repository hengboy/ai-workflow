# Agent Note: Phase-start managed maintenance commit

Status: implemented

[English](2026-11-18-phase-preflight-managed-commit.md) | 中文

## Problem

当上游变更时，阶段启动的自动同步会替换受管工作流指令文件，但阶段会话此前会在这些变更未提交的情况下继续。阶段随后从脏的受管基线开始，之后的 worktree 检出或普通提交可能携带无关的待处理修改。同步核心、钩子、门禁与手动命令有意不执行 Git，钩子无法派发子代理或取得提交权限，而手动同步是独立的显式用户动作，因此没有任何同步组件能够记录刷新后的文件。

## Decision

- 当 `ai-workflow sync-hook --host <current-host> --phase --project <actual-root>` 的阶段结果为继续执行且 `created` 或 `updated` 非空时，同一 planning、coding 或 plan-to-tasks 会话在普通工作前，把恰好这些已报告受管路径委派给 Git Operator 执行一次限定范围的本地维护提交。会话在继续前重新读取更新后的契约。
- Git Operator 只暂存并提交当前分支上已报告的受管路径，保留所有无关的已暂存、未暂存与未跟踪变更。规划产物、任务文件与产品修改绝不包含在内，创建的空目录不是受跟踪路径。
- `skip`、`created` 与 `updated` 均为空，或非继续的 `deny`、`conflict` 或 `failed` 门禁结果，不产生提交、不产生空提交，也不派发 Git。
- 被阻塞或失败的维护提交会以有界支持请求停止阶段，普通项目工作不再继续。
- 维护提交不是实现提交、受审查范围或集成授权。它在交付基线之前落地，不提供审查范围。
- 同步核心（`src/sync/index.ts`、`src/sync/artifacts.ts`、`src/sync/source.ts`）、门禁（`src/sync/gate.ts`）、钩子与插件条目，以及手动 `ai-workflow sync` 命令保持无 Git 且不执行暂存。钩子只接收阶段结果，不能派发子代理、取得审查权限或持有有界写范围；手动同步是独立的显式用户动作，其会话不拥有阶段权限；阶段会话拥有有界的 Git Operator 派发，这是该会话唯一与同步相关的 Git 操作。
- 该规则发布于项目契约及其字节一致镜像、planning、coding 与 plan-to-tasks 技能、`README.md`、`MEMORY.md` 及本记录。

## Alternatives considered

- 让 CLI 或钩子执行提交。放弃原因是钩子在宿主边界运行，无法派发子代理或取得审查权限，而把 Git 移入同步核心会让一条文件替换路径获得提交权限并破坏无 Git 边界。
- 让刷新后的受管文件保持未提交。放弃原因是阶段会从脏的受管基线开始，之后的 worktree 检出或普通提交可能吸收或冲突于无关的待处理修改。
- 在阶段启动时提交所有脏文件。放弃原因是它会暂存无关工作、规划产物、任务文件与产品修改，丢弃操作者待处理的变更，并把一次指令刷新变成不受控的提交。
- 只在实现会话中提交。放弃原因是 planning 与 plan-to-tasks 也会运行阶段检查并接收受管更新，因此这些会话会保留同样的脏基线，并可能把规划产物与受管变更混在一起。
- 从手动同步技能执行提交。放弃原因是手动同步是独立的显式用户动作，不具备阶段范围或审查权限，而自动阶段路径是唯一知道已报告受管路径的地方。

## Consequences

- 阶段从干净的受管基线开始，刷新被记录为一次小型且可审查的维护提交。
- 该提交只包含已报告的受管路径，因此无关的已暂存、未暂存与未跟踪变更仍可用于各自的工作。
- `skip`、空变更集或非继续结果不产生提交也不产生空提交，被阻塞或失败的提交会以有界支持请求停止阶段。
- 同步核心、钩子、门禁与手动命令保持无 Git，且维护提交不是实现提交、受审查范围或集成授权。
- 本记录不取代[项目模板同步](../feature/2026-10-08-project-template-sync.md)、[技能启动时单次同步](../feature/2026-10-09-sync-once-at-skill-start.md)或[同步门禁的紧凑契约引用](./2026-11-18-sync-contract-reference.md)：它们的文件替换、单次启动节奏、紧凑权限引用与同步时不执行 Git 的决策仍然有效。
