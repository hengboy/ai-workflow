# Agent Note: 拆分时冻结任务执行顺序

Status: implemented

[English](2026-09-25-task-execution-order.md) | 中文

## Problem

拆分后的计划没有一份持久化的执行排程。plan-to-tasks 只写每个任务的 `depends_on` 与 `write_scope`，coding 会话在执行时自行推导运行顺序，于是被评审过的任务图并不是真正运行的排程；`coding` 技能甚至要求拆分计划严格串行、一个任务接一个任务地执行。执行前没有任何环节拒绝不一致的顺序：依赖落在自身或更晚阶段的任务、从图中缺失的任务，或同一阶段内写同一路径的两个任务，都可能进入实施，然后以卡住的阶段或写入冲突的形式暴露，而不是作为拆分期缺陷被拦下。把顺序冻结为受校验的工件并按阶段执行，正是缺失的契约。

## Decision

- 拆分时把 `tasks/execution-order.yaml` 冻结为排程：冻结的 `plan_id` 加上有序的非空并行阶段列表，每个阶段是 `- parallel:` 下的非空任务 ID 列表。每个任务恰好出现一次，每个 `depends_on` 目标都位于严格更早的阶段，同一阶段内没有两个任务的归一化写作用域路径相互重叠，因为共享路径与目录包含另一任务的文件都构成冲突。顺序之所以在拆分时冻结，是因为它与任务图一起获得批准，于是 coding 执行的是已评审的顺序，而不是在运行时重新推导依赖，并且同阶段的写作用域在执行前就被证明互不相交。
- plan-to-tasks 把每个任务的阶段计算为其依赖的最晚阶段加一，因此同一深度的任务构成一个并行组；它在审批预览中展示并行阶段与关键路径（最长依赖链），在任务三元组及其配对记录之后、最终 `plan validate` 之前写出排程，且写出的文件与已批准的预览一致。排程没有 `.zh.md` 或 `.i18n.yaml` 兄弟文件；它与 `implementation.yaml` 一样是机器可读的。
- `ai-workflow plan validate --plan <directory>` 在计划目录包含任务文档时加载该排程，并拒绝：文件缺失、`plan_id` 不匹配、YAML 畸形、结构非法、任务 ID 未知、重复或遗漏、依赖位于同一或更晚阶段，以及同一阶段内的写作用域重叠；成功时把有序的阶段 ID 数组报告为 `execution_order`。没有任务文档的计划目录既不要求也不读取该文件，并保持原有输出形状。
- coding 把 `tasks/execution-order.yaml` 当作拆分计划唯一的排程：阶段按文件顺序运行，当前阶段的每个任务在各自任务内先测试后实现并并发派发，整个阶段等待并校验完成后，每个任务的写作用域通过 Git Operator 一次一个提交，然后才进入下一阶段，全部在同一个 worktree 内。当某阶段的校验命令争用共享构建产物时，编排者可以串行化该阶段的派发，而不改变冻结顺序。顺序缺失或非法会在执行前停止运行；coding 绝不从 `depends_on` 重新计算阶段，也绝不回退为串行执行。
- 实现是 `src/workflow/order.ts` 中的 `readExecutionOrder`，由 `src/workflow/types.ts` 的 `TaskPhase` 与 `TaskSchedule` 类型支撑，`src/cli.ts` 仅在有任务的计划中加入 `execution_order` 字段；发布文本是 `templates/skills/plan-to-tasks/SKILL.md` 及其新增的 `references/execution-order.md` 与 `templates/skills/coding/SKILL.md`，标准同时由项目契约模板与本仓库契约、MEMORY 模板与本仓库 MEMORY 以及 `README.md` 声明。
- 排程是 `tasks/` 下新增的非 `.md` 文件，因此任务枚举、双语 sidecar 配对、`plan pairing` 与任务写作用域检查保持原有模式。历史任务集没有排程，因此按设计无法通过新校验：不迁移、不重新生成、不回填，历史单语计划仍像以前一样无法通过。

## Alternatives considered

- **文件缺失或非法时回退为串行执行。** 放弃：已批准的顺序就是执行契约，回退会悄悄运行未经评审的顺序，并掩盖本应阻断运行的拆分期缺陷。
- **在 coding 时从 `depends_on` 重新计算阶段。** 放弃：这会在运行时重新推导已评审的工件，可能产出与批准顺序不同的结果，并把推导逻辑复制进技能，而不是校验一个冻结来源。
- **为每个任务分配独立 worktree 并并发提交。** 放弃：这会成倍增加 worktree 与分支，复杂化合并与清理，并破坏单一 worktree 与串行 Git 的不变量；在同一个 worktree 内按任务写作用域一次一个提交，已经串行化了提交边界。
- **为排程提供 `.zh.md` 与 `.i18n.yaml` 兄弟文件。** 放弃：排程是给 coding 使用的机器可读运行时输入，而不是需要翻译的散文，兄弟文件只会增加配对与校验负担而没有读者。
- **把顺序存进计划或任务 frontmatter。** 放弃：冻结的 `plan.md` 不得编辑，任务 frontmatter 契约保持 `depends_on` 作为依赖的唯一事实来源，因此独立文件才能让排程只有一个权威和一个校验边界。

## Consequences

- coding 会话执行已评审的排程而不是重新推导它：阶段按文件顺序处理，同阶段的写作用域在执行前已被证明互不相交，每个依赖都位于严格更早的阶段。
- 非法顺序永远到不了实施：`plan validate` 会以指明缺陷的错误失败，coding 会话在执行前停止，而不是绕过它继续调度。
- 有任务文档但没有排程的历史任务集按设计无法通过新校验，且本次变更不修复它们；必须重新拆分或显式写出排程才能再次通过，历史单语计划仍像以前一样无法通过。
- 已安装的宿主技能与 agent 是副本，因此新的排程文本只有在下次宿主机安装或 profile 激活后才会进入日常会话；之后实施的第一次拆分就是对阶段调度的运行时观察。
- 相关记录保持有效且不被取代：[双语规划工件记录](./2026-09-17-bilingual-planning-artifacts.md)负责规划工件三元组，本排程不是其中之一，而 [worktree 政策记录](./2026-09-14-project-local-worktree-policy.md) 与 [实施记录](./2026-09-22-plan-implementation-record.md) 保持其规则；没有任何活动记录被整体或部分取代。
