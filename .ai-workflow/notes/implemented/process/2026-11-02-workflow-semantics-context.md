# Agent Note: Workflow semantics, durable state progression and role-scoped context

Status: implemented

English | [中文](2026-11-02-workflow-semantics-context.zh.md)

## Problem

The shipped contract had accumulated contradictory or under-defined statements about routine delegation, review closure, setup recovery and state progression. It also carried a historical 60% and 35,107-code-point size expectation that treated contract completeness as a length gate, and a universal eager-read expectation that made every new session load both navigation files. The rules obscured the difference between execution status, review judgment, test observation, persistence and navigation results, so a successful-looking value could be mistaken for acceptance, and necessary conditional rules could be shortened to satisfy a quota.

## Decision

- State semantics: the project contract is the common authority for delegated execution, review judgment, test observation, implementation-record completion, checkpoint and workspace readiness, gate decisions, synchronization reports and locator results, with each domain's owner, required evidence and permitted next action. Skills and roles apply these definitions while keeping their independent obligations.
- Routine delegation: one accepted task may use fresh scoped Test, implementation and verification delegations at each vertical behavior boundary, proceeding RED1, implementation1, GREEN1, RED2, implementation2 and GREEN2 as needed, while frozen phase order and serial scoped task commits stay unchanged. Expected RED names the intended observable failure and its actual nonzero exit and leaves the GREEN obligation open; routine slices and verification do not consume or expand the post-review repair and recheck budget. Completed sessions are never reused or resumed.
- Review outcomes: a completed review may report execution `done` while its verdict is non-PASS; `PASS` is permitted with advisories visible when every advisory has a reasoned disposition and no unresolved blocker remains. Missing required inputs are `blocked`, execution failure is `failed`, and no successful-looking status substitutes for acceptance.
- Setup recovery: actual adoption state selects ordinary `init` for a project with no adoption and `init --upgrade` only when the adoption and its prerequisites exist. Missing prerequisites return exact paths without overwriting local data, and neither directory presence nor the preflight authorizes setup.
- No contract quota: the contract retains every distinct rule, exception, responsibility, evidence and recovery path and may grow as needed. No fixed character, line, byte or reduction percentage is an acceptance gate, the historical 60% and 35,107-code-point measurements are historical and are not current gates, report-body targets remain separate from contract length, and the source contract and its tracked mirror stay byte-identical. Contract content is never truncated to satisfy a report target.
- Role-scoped context: every participating role loads its repository's full applicable contract, every non-Spec role loads `MEMORY.md`, and each role loads the additional context its published matrix requires. Primary orchestration and discovery use the navigation catalog to locate a feature and verify a known feature with the locator before source discovery, and navigation JSON is read only for an authorized investigation or maintenance or a needed bounded entry. Read scope is permission, not an eager-read list; a verified locator is reusable only while its provenance and relevant state stay current; a fresh session never counts a parent's read as its own; and a role without shell requests the primary to arrange lookup.
- The delivered surfaces are `templates/project/AGENTS.md` and its byte-identical `.ai-workflow/AGENTS.md` mirror, the contract loading entry, the affected skills and nine role templates, `README.md`, `MEMORY.md` and curated navigation. The content tests are static delivered-text evidence and do not prove native model compliance, runtime enforcement or a measured performance gain.

## Alternatives considered

- **Keep the historical size target as a completeness proxy.** Declined: a length ratio cannot distinguish a retained obligation from dropped prose, so it could force truncation of necessary rules or reward deletion instead of completeness; retained-obligation checks and mirror equality are the durable boundary.
- **Keep universal eager navigation loading for every session.** Declined: it forces irrelevant reads and conflicts with the role matrix and the read-scope permission model; the catalog, locator provenance and bounded-entry rule carry the needed navigation without a blanket self-read.
- **Collapse the state domains into one success value.** Declined: execution completion, review judgment, test observation, persistence and navigation results have different owners and evidence, and merging them would let a checkpoint or `done` report stand in for acceptance.
- **Resolve routine delegation through one role dispatch per task.** Declined: a single role dispatch per task cannot carry multiple vertical RED/GREEN boundaries, and the frozen phase order and serial commit boundaries already bound the work without a second-dispatch prohibition.
- **Apply the rules only in skills and roles and leave the contract thin.** Declined: common leaf obligations must remain in the applicable contract, with primary-only detail referenced from the Coding authority, so a thin contract would lose shared authority.

## Consequences

- The contract now states one consistent set of state, review, setup, delegation and context rules, and its source and tracked mirror remain byte-identical while every distinct obligation and conditional example stays present.
- Routine implementation can advance one vertical slice at a time with fresh scoped delegations, while review closure, blockers, persistence and workspace readiness keep their separate evidence requirements.
- Navigation stays a bounded catalog backed by authoritative JSON, and each role loads only its matrix context; the universal eager-read expectation is removed without reducing the required contract or MEMORY authority.
- The historical 60% and 35,107-code-point measurements in earlier records are retained as history and are no longer acceptance gates; current completeness is checked by retained distinct obligations, mirror equality and conditional content.
- The shipped-content, installation and CLI checks are static evidence. They do not establish native three-host compliance, a runtime fix or a measured context or performance gain.
