# Agent Note: Parent workspace coding orchestration

Status: implemented

English | [中文](2026-10-09-workspace-coding-orchestration.zh.md)

## Problem

Planning could freeze a cross-repository workspace plan and the skills could point to a fresh parent session, but the shipped workflow still had no delivered parent-side execution. Coding instructed a manual session in every participating repository, the implementation record had no task-level checkpoint protocol, and `workspace status` reported only a singular advisory `next_repository` over a filtered slice schedule. Nothing defined how one parent session activates the boundary, prepares the split, dispatches native leaves into per-repository worktrees, preserves the frozen parent phases and delivery barriers, writes per-task checkpoints through one filesystem command, separates a per-repository delivery review from the finalization review, or bounds recovery when a phase is interrupted.

## Decision

- Activation is exact: only a frozen plan that declares at least one participating non-root repository matched to the current root's `.gitmodules` enters parent orchestration. An ordinary plan, a root-only workspace plan whose `workspace_repos` declares only the reserved `workspace` root entry, and a project with `.gitmodules` running a non-participating plan all keep the existing direct, mechanical, unsplit or split route unchanged.
- The one primary parent Coding session owns orchestration. When its frozen child-participating plan has no task set, the session invokes `plan-to-tasks` as an approved preparation procedure that shows the full approval preview, writes and validates the task triplets, the schedule and `workspace.yaml`, runs `ai-workflow workspace distribute --plan <directory>`, and returns control to the same session; a standalone plan-to-tasks invocation still ends. No nested splitter, coordinator, remote session or child host process exists, and declining approval creates no tasks, slices, worktrees or implementation records.
- Each active repository owns exactly one run-owned worktree per active repository at `<source-root>/.worktrees/<planId>` on branch `ai-workflow/<planId>`; the parent worktree is not a container for child implementation and its submodule directories stay empty. Git Operator alone runs Git, verifies each repository's real Git common directory so a matching directory name does not prove identity, materializes its ignored state, checks each scoped task commit's exact parentage and both rename endpoints against the task write scope, performs the non-fast-forward delivery integration, and cleans up only run-owned worktrees and branches.
- The original parent `tasks/execution-order.yaml` remains the only global schedule. Its phases run in file order; the independent tasks of the current phase are dispatched concurrently and the whole phase is awaited and verified before its scoped commits are written serially, and a repository reaching its last task phase completes a per-repository delivery gate before a dependent repository advances. A filtered slice schedule or a recomputed DAG grants no dispatch authority.
- Each repository keeps its single `implementation.yaml`, and the new fields exist only on a new workspace execution record. `execution` carries the purpose (`tasks` versus root-only `finalization`), canonical `source_root`, `repository`, absolute `worktree`, `branch`, `target_branch` and repository-local `base_commit`; `task_checkpoints` maps each local frozen task ID to a writing `kind: commit` with its full SHA or to a verified unchanged `kind: no-change` with the exact HEAD; a purpose-scoped `reviewed_commit` records the exact resolved current-purpose HEAD. The record still exposes only the two top-level statuses `in-progress` and `completed`.
- `ai-workflow workspace checkpoint --plan <directory> --repo <name>` is the only writer. It accepts exactly one JSON event on stdin — `start`, `task`, `reviewed`, `delivered` or `finalized` — rejects unknown fields, wrong types, a wrong plan or repository, unauthorized task IDs, contradictory duplicates, invalid transitions and malformed full SHAs before writing, is idempotent for identical repeats, and publishes through the shared atomic writer so a refusal leaves the prior record byte-unchanged. It stays filesystem-only; the primary calls it only after the required Git Operator and review results, and no temporary input file, central ledger or extra run record is introduced.
- After a repository's last task phase the primary completes its per-repository delivery review and delivery gate for that repository's task scope, and finalization later runs a separate finalization review that does not re-review delivered tasks. Root-prefix delivery keeps the same record `in-progress` with `root_tasks_commit` until the pointer finalization, and a finalization-only run executes zero tasks.
- Recovery is bounded: automatic resume is supported only at a clean, fully checkpointed phase boundary or a verified repository delivery boundary. A dirty partial phase, a commit-without-checkpoint gap, unknown future-phase progress, an uncertain review result, a contradictory record or an unrelated target drift stops with a bounded support or recovery request instead of redispatch; recorded tasks are not blindly dispatched again, and a lost merge completion is reconstructed only from an exact reviewed head, the target baseline, expected merge parentage and owned-cleanup evidence.
- An optional `workspace_finalization` frontmatter declares root-owned finalization coverage on a child-participating plan: `requirements` and `acceptance_criteria` disjoint from every task AC, repository-qualified `read_scope` entries, a root-relative `write_scope` that cannot enter a participating repository, and `test_commands`. Finalization coverage never becomes a task and never joins the execution order, so complete plan coverage is the union of task coverage and finalization coverage and the manifest's root subset equals root task coverage plus that declaration.
- A child-participating `workspace status` report adds an `execution` projection: the one-based current parent `phase` or `null`, that phase's `pending_tasks` with `task`, `repo` and absolute `repository_path` and `plan_path`, the `awaiting_delivery` repositories, `blockers` and `completed`. The existing `order` and `next_repository` remain advisory.

## Alternatives considered

- **Run a separate Coding session in each participating repository.** Declined: it is the manual per-child route this change replaces, it cannot enforce the frozen global phases or the repository delivery barriers from one place, and it cannot show dependency-correct delivery before dependents advance.
- **Add a scheduler service, nested coordinator role or remote provider executor.** Declined: the native parent already is the sole executor, so a scheduler or coordinator would add an unsupported runtime surface and a second source of dispatch truth without improving the frozen schedule.
- **Recompute the global schedule from `depends_on`, or let a filtered slice schedule advance independently.** Declined: the frozen `tasks/execution-order.yaml` is the only global schedule, and a recomputed DAG or a slice-local phase number would let a repository run ahead of the active parent phase and bypass a delivery barrier.
- **Model the checkpoint protocol as a distributed transaction with Git.** Declined: the single-record writer is filesystem-only and intentionally does not claim atomicity with Git, so a partial delivery is retained and reported with its actual state instead of an unimplemented rollback guarantee.
- **Treat a dirty partial phase as resumable pending work.** Declined: uncommitted output from another task is indistinguishable from an incomplete write, so automatic continuation is limited to clean, evidenced boundaries and the dirty case stops with a bounded support request.

## Consequences

- The delivered scope is covered by automated tests: the checkpoint CLI and single-repository compatibility tests (`tests/integration/workspace-checkpoint-cli.test.ts`, `tests/integration/workspace-single-repo-compatibility.test.ts`), the projection unit tests (`tests/unit/workspace-execution.test.ts`), the real-Git lifecycle and final-tree tests (`tests/integration/workspace-coding-git.test.ts`, `tests/integration/workspace-finalization-git.test.ts`) and the shipped-content tests (`tests/behavior/workspace-workflow-content.test.ts`, `tests/behavior/change-routing.test.ts`, `tests/behavior/workspace-planning-content.test.ts`). These prove deterministic record and projection behavior, the exercised Git procedure and the shipped instructions; they do not prove a live model's native delegation.
- The three-host native acceptance is not fully demonstrated in this run. It requires an actual parent native session per host — OpenCode, Claude Code and Codex — started with disposable fixtures and a disposable host HOME, and the available run did not complete that parent-session delegation smoke. Automated CLI, real-Git and content coverage is complete for the delivered scope, but the native parent-to-leaf tool trace remains an outstanding, explicitly reported gap and blocker; unavailable authentication or trust is not converted into a pass.
- This record partially supersedes the manual per-repository session wording in [the submodule workspace delivery record](../architecture/2026-09-30-submodule-workspace.md), [the Planning and coding session boundary record](../process/2026-09-23-planning-coding-session-boundary.md), [the workspace split distribution handoff record](../process/2026-10-02-workspace-distribute-handoff.md), [the workspace session handoff record](../bug-fix/2026-10-08-workspace-session-handoff.md) and [the workspace execution consistency record](../bug-fix/2026-10-08-workspace-execution-consistency.md). Each keeps its decision, rationale and evidence limits, and its current execution fact points here.
- Ordinary and root-only behavior is unchanged: a project without `.gitmodules`, an ordinary plan in a project with `.gitmodules`, and a root-only workspace plan keep their direct, mechanical, unsplit or split route, their one-worktree lifecycle, their record shape and their CLI output, and gain no child-specific artifact or command.
