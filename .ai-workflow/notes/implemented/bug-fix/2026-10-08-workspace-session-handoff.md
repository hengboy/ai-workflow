# Agent Note: Workspace session handoff after Planning and splitting

Status: implemented

English | [中文](2026-10-08-workspace-session-handoff.zh.md)

## Problem

The shipped next-session guidance stopped at one unconditional route. Planning's completion checklist, the `coding` skill's no-frozen-plan path and the README told every planned change to start a new session and invoke the coding skill. That route is wrong once a workspace plan declares at least one non-root participating repository, because such a plan must be split by plan-to-tasks and distributed before any repository can implement a slice. A user following the old text would enter a coding session for a plan no child had received, and the coding entry would then refuse the undistributed plan, wasting the session. The same gap left the plan-to-tasks split completion without a next-Coding handoff, the coding slice completion without a next-repository or finalization handoff, and the finalization rules without the `ready_for_finalization` readiness report and the new-root-session step.

## Decision

- Planning's `## Completion checklist` routes conditionally by `workspace_repos`: a plan that declares at least one non-root participating repository tells the user to start a new session at `<workspace-root>` and invoke plan-to-tasks with the absolute frozen plan directory, then run `ai-workflow workspace distribute --plan <directory>` after validation and before implementation, and to not invoke coding yet; an ordinary plan or a root-only workspace plan whose `workspace_repos` declares only the reserved workspace root entry tells the user to start a new session and invoke the coding skill. Planning reports the absolute project or workspace root, the frozen plan directory, the `plan validate` result and each participant's name, path and `depends_on` order, and includes a copyable prompt.
- The `coding` skill's `## Change routing` no-frozen-plan path follows the same split: a workspace plan routes through plan-to-tasks and distribution, an ordinary or root-only plan routes to the coding skill, and the planning session still creates no worktree, no implementation record, no implementation or review dispatch and no commit.
- The coding entry and slice rules identify the parent workspace root session and the absolute parent workspace plan directory: an undistributed plan directs to plan-to-tasks when the plan still needs splitting or to a rerun of `ai-workflow workspace distribute --plan <directory>` when the split artifacts exist, and a participating repository with no slice manifest names the same distribution rerun as its repair.
- Plan-to-tasks `## Workspace split` completion reports each participating repository's name, path and slice state (`written` or `unchanged`), the validation and distribution result, the reserved root entry (state workspace-root, not written or unchanged, because its tasks stay in the root plan), the frozen `delivery order` including root tasks, and `ai-workflow workspace status --plan <directory>` read against the parent workspace plan directory. It ships a copyable text prompt that invokes the coding skill at the working directory `<repository-root>`, implements only this repository's tasks from the local frozen plan directory `<repository-plan-directory>` in frozen order, and runs `ai-workflow workspace status --plan <workspace-plan-directory>` against the original parent. The frozen delivery phases come from `tasks/execution-order.yaml` and each repository's `depends_on`; `workspace status`'s `next_repository` now follows that frozen repository first-appearance order, including the pending root-owned tasks, so it agrees with the frozen schedule rather than overriding it, and root-owned tasks keep their place and can precede dependent children.
- Coding slice completion reports the delivery SHA and runs `ai-workflow workspace status --plan <directory>` with the absolute parent workspace plan directory to hand off the next repository, path, session and prompt in the frozen delivery order, reusing the split handoff's `<repository-root>`/`<repository-plan-directory>`/`<workspace-plan-directory>` conventions. Finalization requires both every child slice `present` and `completed` and the root-owned task delivery boundary satisfied, so a child session never finalizes by itself.
- The `coding` skill's `## Workspace finalization` keeps the read-only Git delivery-commit verification and pin restrictions and adds the `ready_for_finalization` report; finalization consumes it only when `valid` is true and every child slice is `present` and `completed`, together with the root entry's `tasks_delivered` (the single-record `root_tasks_commit` delivery boundary) and the read-only Git delivery-commit verification, all read against the original parent `<workspace-plan-directory>`. A child or other repository session reports the copyable next-root prompt, while an already-running correct parent finalization session performs the finalization without reopening itself; the prompt invokes the coding skill at `<workspace-root>`, runs `ai-workflow workspace status --plan <workspace-plan-directory>`, and pins only after those conditions hold.
- `README.md`, `MEMORY.md` and `templates/project/MEMORY.md` carry the same conditional routing, so no stale unconditional coding handoff remains.

## Alternatives considered

- **Keep one unconditional coding handoff and let the coding entry re-route.** Declined: the coding entry would refuse the undistributed plan only after the user had already started the wrong session, so the refusal is a dead-end round trip instead of the correct next action.
- **Distribute from the planning session.** Declined: planning owns only the workspace-root `spec.md`/`plan.md` pair and never writes a slice, and distribution needs the split's task triplets, pair records and `workspace.yaml`, so distribution belongs to the plan-to-tasks split session, matching the existing distribution handoff record.
- **Prescribe children-first delivery after a split.** Declined: root-owned tasks keep their frozen place in `tasks/execution-order.yaml` and may precede dependent children, so a children-first instruction would contradict the frozen order.
- **Add a new command or JSON field for the handoff.** Declined: `ai-workflow workspace status --plan <directory>` already reports `ready_for_finalization` and `next_repository`, so only the guidance needed to catch up with the existing output.
- **Rebuild the whole navigation index from discovery.** Declined: the repository already ships broad auto-discovered features (`root`, `src`, `tests`), and a discovery rebuild would replace the curated index and could not add this bounded feature, so the update preserves the existing features and adds one instead.

## Consequences

- Planning, plan-to-tasks and coding routing, plus `README.md`, `MEMORY.md` and `templates/project/MEMORY.md`, now agree on the conditional workspace-aware handoff, and the old unconditional single-route fact is gone.
- Shipped-template content is guarded by `tests/behavior/change-routing.test.ts`, `tests/behavior/workspace-planning-content.test.ts` and `tests/behavior/workspace-workflow-content.test.ts`, which assert the skill, README and MEMORY text including the shipped text-fence prompts; the evidence scope is shipped text, not runtime execution of a multi-repository split.
- The navigation index gains one bounded `workspace-handoff` feature that points at the three skill files, their references, `README.md`, both `MEMORY.md` files and the three behavior tests, with the existing module-root definitions preserved.
- This record partially supersedes the unconditional single-session handoff fact in [the Planning and coding session boundary record](../process/2026-09-23-planning-coding-session-boundary.md) and adds context to [the workspace split distribution handoff record](../process/2026-10-02-workspace-distribute-handoff.md); both records keep their decisions and rationale, and their current handoff facts point here.
- This record's child-only readiness and advisory `next_repository` facts are partially superseded by [the workspace execution consistency record](./2026-10-08-workspace-execution-consistency.md), which records the manifest validation, the frozen-order `next_repository`, the root entry's `tasks_delivered`/`delivery_commit` and `root_tasks_commit`; this record keeps its conditional handoff decision and rationale, and its current delivery-boundary fact points there.
- [The workspace coding orchestration record](../feature/2026-10-09-workspace-coding-orchestration.md) partially supersedes this record's handoff wording with the delivered parent-session preparation, per-repository worktrees, checkpoint command and separated reviews; this record keeps its conditional handoff decision and rationale.
