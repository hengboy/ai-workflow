# Project memory

## Standards

- Requests are routed before work starts: a small requirement, feature adjustment or defect fix with clear, bounded intent is implemented directly without Planning or the dual-axis review, while a new feature, unclear or contested requirements, or a public-interface, persistent-format, cross-module, cross-stack, migration, compatibility or contract change runs Planning and keeps that review gate. Direct and mechanical changes still execute as one coding execution unit with its worktree and Git Operator commit; a planned change without a frozen plan is planned first and then handed off, so the planning session ends with the frozen plan path and an instruction to start a new session and invoke the coding skill instead of starting implementation; the routing standard lives in `.ai-workflow/AGENTS.md`, the `coding` and `planning` skills, `templates/project/MEMORY.md` and `README.md`.
- Coding must create one project-local temporary worktree under `<project>/.worktrees/<name>` before implementation; all implementation, validation and per-step commits happen inside that single worktree, with `.worktrees/` in `.gitignore`. Git Operator materializes the project's entire gitignored state into the worktree (excluding the `.worktrees/` container), so the frozen plan, `MEMORY.md`, navigation, notes, dependencies and build outputs stay visible and single-source at the project root.
- A split plan's execution order is frozen at split time as `tasks/execution-order.yaml`: the ordered list of non-empty parallel phases that covers every task exactly once, with every dependency in a strictly earlier phase and no overlapping normalized write-scope paths inside one phase (directory containment included). Plan-to-tasks previews the phases with the critical path and writes the file after the task triplets and their pair records; `ai-workflow plan validate --plan <directory>` reports `execution_order` and fails on a missing or invalid order. Coding treats the file as the only schedule for a split plan: phases run in file order, every task of a phase is dispatched concurrently inside the single worktree with test work before implementation in each task, and each task's write scope is committed serially through Git Operator one commit at a time before advancing; a missing or invalid order stops the run before execution, with no serial fallback and no recomputation from `depends_on`. The schedule is machine-readable and has no `.zh.md` or `.i18n.yaml` sibling, and pre-existing task sets without it fail validation by design with no migration.
- The complete project workflow contract lives in `.ai-workflow/AGENTS.md`, single-sourced from `templates/project/AGENTS.md`, and applies to the entire project and every participating agent. Host installation only adds one short loading entry between `<!-- ai-workflow:begin -->` and `<!-- ai-workflow:end -->` in each global instruction file (opencode `~/.config/opencode/AGENTS.md`, claude `~/.claude/CLAUDE.md`, codex `~/.codex/AGENTS.md`), single-sourced from `templates/contract/AGENTS.md`; that entry requires an explicit read of the project contract and never assumes that a host recursively loads hidden directories or follows Markdown links. A missing project contract is reported with the `ai-workflow init <project-root> --upgrade` entry instead of a global fallback. Root-level `AGENTS.md`/`CLAUDE.md` stay user-owned; the `update` subcommand and `.ai-workflow/project-manifest.json` are removed; `ai-workflow init` writes `MEMORY.md`, `.ai-workflow/**` and `.gitignore`.
- This repository tracks `.ai-workflow/**` and `MEMORY.md`; only `.ai-workflow/plans/` and `.worktrees/` are gitignored, and it ships no root `AGENTS.md`/`CLAUDE.md`, so agent guidance exists only in the user-level loading entry and the project contract.
- Documentation Maintainer owns explicitly scoped documentation only: `MEMORY.md`, navigation indexes, README files, notes under `.ai-workflow/notes/` and other non-code documentation. It does not edit source, tests, schemas, frozen plans or task files, and returns exact paths and validation evidence to the primary orchestrator for Git Operator.
- When documenting architecture or module boundaries, use English structural elements and explicitly name modules, boundaries, ownership and related structural terms; prose language preferences do not translate structural elements.
- Agent Notes under `.ai-workflow/notes/` are the only active proposal and decision mechanism and the single current governance source, reached through `.ai-workflow/notes/AGENTS.md` and governed by `.ai-workflow/notes/README.md`. The retired mechanism has no command, alias, conversion or fallback; any residual history files are never read, listed or validated. This file records current standards (how) and notes record why, so both stay consistent in the same change.
- Every Agent Note is a complete bilingual triplet in one directory: the English `<note>.md`, the Chinese `<note>.zh.md` and the `<note>.i18n.yaml` consistency record holding each side's git blob hash. Both languages carry equal authority, mirror each other's heading, code, table, list and link structure, and carry the required language switchers; only prose is translated while structural elements stay English. `ai-workflow notes pairing` verifies pairs and `--write <note>` (or `--write --all`) records them; `notes validate` and archive sealing cover all three artifacts.
- Planning artifacts are complete bilingual triplets as well, enforced by `ai-workflow plan validate --plan <directory>` and recorded by `ai-workflow plan pairing --plan <directory>`. Every `spec.md`, `plan.md` and `tasks/task-NNN-slug.md` carries a `.zh.md` counterpart and a `.i18n.yaml` consistency record; the English side alone carries the YAML frontmatter, `REQ-###`/`AC-###` identifiers, counts and the `digest`, both sides mirror each other's structure, and only `task-NNN-slug.md` counts as a task document. The planning skill's numbered workflow writes all six files and treats `plan validate` as a hard completion gate, so `spec.md` or `plan.md` is never frozen without its `.zh.md` and `.i18n.yaml`. Explicit `--write` selections are fully pre-checked before any record is written and `--write --all` records only complete pairs. Existing single-language plans under `.ai-workflow/plans/` are not migrated, converted or exempted: they fail the new validation by design and stay byte-unchanged, so a plan frozen under the old single-language format is an expected legacy artifact rather than a new defect.
- The `output_language` feature was removed entirely: `config.yaml` carries only the optional `active_profile` field, install writes skills and role agents byte-for-byte from their templates with no injected prose-language directive, and a leftover `output_language` key is an unknown key that fails configuration validation before any write. Agent Notes and planning artifacts remain always-complete bilingual triplets, while structural elements, field names, fixed headings, `Status` and its values, file paths and dates remain English.
- Navigation JSON is authoritative and Markdown is generated from it.
- Coding creates no workflow manifest or run record other than the single implementation record at `<project>/.ai-workflow/plans/<planId>/implementation.yaml`, which holds `plan_id` with `status: in-progress` and an ISO 8601 `started_at` in the UTC+08:00 timezone before the first implementation step and becomes `status: completed` with an ISO 8601 `completed_at` in the UTC+08:00 timezone and the final commit SHA after the final merge and owned cleanup; it is the only permitted run record. The record has only the two status values `in-progress` and `completed`.
- Host agent frontmatter stays host-native and is rendered from each template's `tools:` declaration: Codex uses TOML `model`/`model_reasoning_effort`, Claude uses `allowed-tools`, and OpenCode supports both `v1` (`mode: subagent` with singular `permission:` using `bash`/`task`) and `v2` (`mode: subagent` with ordered `permissions` rules using `shell`/`subagent`) selected by `--opencode-version v1|v2|auto` (`install`/`profile activate` default `auto` via `opencode --version`, library default `v2`), where the template `search` tool maps to `glob` plus `grep`, `web` maps to `webfetch` plus `websearch`, and every role denies nested dispatch (`task` in v1, `subagent` in v2) because only the primary orchestrator dispatches. OpenCode `hidden: true` removes an agent from the subagent catalog and blocks the `subagent` tool, so no dispatchable role may set it; that catalog requirement is guarded by `tests/behavior/opencode-agent-contract.test.ts`.
