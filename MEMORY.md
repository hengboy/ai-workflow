# Project memory

## Standards

- Requests are routed before work starts: a small requirement, feature adjustment or defect fix with clear, bounded intent is implemented directly without Planning or the dual-axis review, while a new feature, unclear or contested requirements, or a public-interface, persistent-format, cross-module, cross-stack, migration, compatibility or contract change runs Planning and keeps that review gate. Direct and mechanical changes still execute as one coding execution unit with its worktree and Git Operator commit; a planned change without a frozen plan is planned first and then handed off, so the planning session ends with the frozen plan directory and its `plan validate` result without starting implementation; a plan that declares at least one non-root participating repository hands off to a new session at the workspace root that invokes plan-to-tasks and runs `ai-workflow workspace distribute --plan <directory>` before implementation, while an ordinary or root-only plan hands off to a new session that invokes the coding skill; the routing standard lives in `.ai-workflow/AGENTS.md`, the `coding` and `planning` skills, `templates/project/MEMORY.md` and `README.md`.
- Coding must create one project-local temporary worktree under `<project>/.worktrees/<name>` before implementation; all implementation, validation and per-step commits happen inside that single worktree, with `.worktrees/` in `.gitignore`. Git Operator materializes the project's entire gitignored state into the worktree (excluding the `.worktrees/` container), so the frozen plan, `MEMORY.md`, navigation, notes, dependencies and build outputs stay visible and single-source at the project root.
- A split plan's execution order is frozen at split time as `tasks/execution-order.yaml`: the ordered list of non-empty parallel phases that covers every task exactly once, with every dependency in a strictly earlier phase and no overlapping normalized write-scope paths inside one phase (directory containment included). Plan-to-tasks previews the phases with the critical path and writes the file after the task triplets and their pair records; `ai-workflow plan validate --plan <directory>` reports `execution_order` and fails on a missing or invalid order. Coding treats the file as the only schedule for a split plan: phases run in file order, every task of a phase is dispatched concurrently inside the single worktree with test work before implementation in each task, and each task's write scope is committed serially through Git Operator one commit at a time before advancing; a missing or invalid order stops the run before execution, with no serial fallback and no recomputation from `depends_on`. The schedule is machine-readable and has no `.zh.md` or `.i18n.yaml` sibling, and pre-existing task sets without it fail validation by design with no migration.
- A git-submodule workspace root delivers one cross-repository plan: the root freezes the single `spec.md`/`plan.md` pair whose `workspace_repos` frontmatter and `workspace.yaml` manifest assign every task to exactly one repository in a repository-level delivery order. Declared `.gitmodules` submodule paths are excluded from the root's navigation discovery and validation, and a pre-existing workspace navigation is refreshed only with `ai-workflow context rebuild --project <root> --write`. `ai-workflow workspace distribute --plan <directory>` writes each participating repository's self-contained slice and refuses divergences before writing, while `ai-workflow workspace status --plan <directory>` validates the workspace manifest before reporting `valid`, reports each repository's slice, implementation-record and delivery-commit state, a `workspace_root_entry` with `record`, `tasks_delivered` and a nullable `delivery_commit`, and an `order` and `next_repository` that follow the frozen `tasks/execution-order.yaml` repository first-appearance order including pending root tasks, all without writing. A workspace plan that declares at least one non-root participating repository must be split by plan-to-tasks before implementation, and completing that split runs `ai-workflow workspace distribute --plan <directory>` after the task triplets, their pair records and `workspace.yaml` are written and `ai-workflow plan validate --plan <directory>` passes; a workspace plan whose `workspace_repos` declares only the reserved `workspace` root entry may be implemented unsplit. After all slices complete, verify each recorded delivery commit read-only and pin each affected submodule in the workspace worktree with `git update-index --cacheinfo 160000,<sha>,<path>`, staging only authorized pointer paths and workspace-root files. The workspace root owns the cross-repository decision note, each repository owns its own delivered-facts note, and cross-repository references stay plain plan-ID text. Planning ends a cross-repository workspace plan by routing to a new session at the workspace root that invokes plan-to-tasks; a child record counts as delivered only when its `record` is `completed`, its slice is `present`, its `plan_id` matches and its `delivery_commit` is a full commit SHA, and `ready_for_finalization` combines every such child with the root `tasks_delivered`, so the root Git Operator verifies every delivery commit with a read-only `git cat-file -e <sha>^{commit}` existence check before any index mutation and pins it. The root's own tasks are delivered as an optional `root_tasks_commit` in the same root `implementation.yaml`, which stays `in-progress` until finalization, so the workflow keeps one record with only `in-progress` and `completed`, and an already-running correct root finalization session executes directly instead of reopening itself. Planning keeps the reserved `workspace` root a dependency-free `prefix` delivered separately from finalization, requires cross-repository acceptance criteria to name their owning repository with exact bounded read-only source checks, never checks out a child automatically, and keeps root owner notes separate from child delivered facts.
- The complete project workflow contract lives in `.ai-workflow/AGENTS.md`, single-sourced from `templates/project/AGENTS.md`, and applies to the entire project and every participating agent. Host installation only adds one short loading entry between `<!-- ai-workflow:begin -->` and `<!-- ai-workflow:end -->` in each global instruction file (opencode `~/.config/opencode/AGENTS.md`, claude `~/.claude/CLAUDE.md`, codex `~/.codex/AGENTS.md`), single-sourced from `templates/contract/AGENTS.md`; that entry requires an explicit read of the project contract and never assumes that a host recursively loads hidden directories or follows Markdown links. A missing project contract is reported with the `ai-workflow init <project-root> --upgrade` entry instead of a global fallback. Root-level `AGENTS.md`/`CLAUDE.md` stay user-owned; the `update` subcommand and `.ai-workflow/project-manifest.json` are removed; `ai-workflow init` writes `MEMORY.md`, `.ai-workflow/**` and `.gitignore`.
- This repository tracks `.ai-workflow/**` and `MEMORY.md`; only `.ai-workflow/plans/` and `.worktrees/` are gitignored, and it ships no root `AGENTS.md`/`CLAUDE.md`, so agent guidance exists only in the user-level loading entry and the project contract.
- Adopted projects synchronize their workflow instructions from the fixed upstream source `hengboy/ai-workflow` branch `simplify`. `ai-workflow sync [project]` and `ai-workflow init --upgrade` patch only the six marked `templates/project` Markdown templates — `templates/project/AGENTS.md`, `templates/project/MEMORY.md`, `templates/project/notes/AGENTS.md`, `templates/project/notes/README.md`, `templates/project/notes/implemented/AGENTS.md` and `templates/project/notes/archived/AGENTS.md` — through `<!-- ai-workflow:section <id>:begin/end -->` ownership markers, preserving every byte outside a section, adopting an exact unmarked same-heading legacy section, inserting a clearly absent section once, retaining a retired file and any differing or unknown unmarked content with a `needs_attention` warning, and publishing each file atomically. `src/sync/source.ts` resolves the branch HEAD once, requires one immutable 40-hex commit, validates the listing and every supported file at that commit, and reads `GH_TOKEN` before `GITHUB_TOKEN` into an explicit bearer header; a failed or incomplete retrieval leaves target bytes unchanged and reports `unverified` with `verified: false` and `proceed: true` (exit 2). `src/sync/merge.ts` (`mergeOwnedSections`, `validateOwnedSections`, `OwnershipConflictError`) and `src/sync/index.ts` (`applyTemplateSnapshot`, `synchronizeProject`, `reconcileIgnoreFile`, `notesStructureDirectories`) hold the shared core, which `upgradeProject` reuses with the shipped local templates and a null source commit, so local upgrade reports `needs_attention` with an unverified local-source warning and makes no upstream freshness claim while retaining its missing-prerequisite conflict and exact retired-ADR imperative guard. Statuses and exit codes are `synchronized` 0, `unverified`/`needs_attention` 2 and `pending`/`conflict`/`failed` 1; `--check` proposes without writing, structural conflicts write nothing, and a publication failure restores invocation-local originals and removes only invocation-created artifacts. Synchronization stores no baseline, keeps generated navigation, the archive manifest and note triplets preserved, and performs no Git operation; the additive automatic host-triggered entries built on this shared core are described in the next standard.
- OpenCode, Claude Code and Codex share the synchronization core through additive native host entries. `ai-workflow install` registers only owned entries — the auto-loaded OpenCode plugin `.config/opencode/plugins/ai-workflow-sync.js` rendered from `templates/hooks/opencode.js`, and context plus `PreToolUse` hook commands in `~/.claude/settings.json` and `~/.codex/hooks.json` — and every entry invokes `ai-workflow sync-hook --host <host>`; `uninstall` removes only those owned entries and files while preserving unrelated hooks and settings. `src/sync/gate.ts` (`runProjectGate`, `ProjectGateInput`, `ProjectGateOptions`, `ProjectGateResult`) resolves the actual adopted root, keys a unit by native session or by project for `PhaseEntry`, invalidates it on session start, user turn, resume and actual-root change, reuses one parent snapshot for same-root children, exempts only its own sync actor and the updated-authority read, and maps a report to `allow`, `deny` or `skip`. `src/install/hooks.ts` (`installSynchronization`, `uninstallSynchronization`, `synchronizationPath`, `SynchronizationRecords`) owns the additive install, refresh and uninstall semantics. The CLI `sync-hook` prints the raw gate JSON for the `--phase` form on every host and for the OpenCode stdin gate, emits host-native Claude Code and Codex stdin output (`PreToolUse` deny via `hookSpecificOutput.permissionDecision`; a `UserPromptSubmit` block with a top-level `decision` of `block` and `reason`) that never exposes the raw `allow`/`deny`/`skip` decision, and always exits 0 for handled results; the raw form's top-level `decision` (`allow`, `deny` or `skip`) has `status`, `verified` and `proceed` inside its optional nested `report`, the host follows its own protocol, and the manual `ai-workflow sync` command prints a `SyncReport` with `status`, `verified` and `proceed` and no `decision`. After a safe patch changes the contract, the gate exposes the updated authority for explicit read or injection before ordinary work; `conflict` and `failed` block, and warnings proceed without a freshness claim. Codex hooks require human trust, OpenCode requires a restart, and a disabled, untrusted, unloaded or duplicate host-scoped skill is reported as not active rather than auto-approved; `templates/skills/sync-ai-workflow/SKILL.md` is the shipped safe manual skill and a shadowing host-scoped copy is preserved and reported for one-time resolution, never deleted blindly.
- Documentation Maintainer owns explicitly scoped documentation only: `MEMORY.md`, navigation indexes, README files, notes under `.ai-workflow/notes/` and other non-code documentation. It does not edit source, tests, schemas, frozen plans or task files, and returns exact paths and validation evidence to the primary orchestrator for Git Operator.
- When documenting architecture or module boundaries, use English structural elements and explicitly name modules, boundaries, ownership and related structural terms; prose language preferences do not translate structural elements.
- Agent Notes under `.ai-workflow/notes/` are the only active proposal and decision mechanism and the single current governance source, reached through `.ai-workflow/notes/AGENTS.md` and governed by `.ai-workflow/notes/README.md`. The retired mechanism has no command, alias, conversion or fallback; any residual history files are never read, listed or validated. This file records current standards (how) and notes record why, so both stay consistent in the same change.
- Every Agent Note is a complete bilingual triplet in one directory: the English `<note>.md`, the Chinese `<note>.zh.md` and the `<note>.i18n.yaml` consistency record holding each side's git blob hash. Both languages carry equal authority, mirror each other's heading, code, table, list and link structure, and carry the required language switchers; only prose is translated while structural elements stay English. `ai-workflow notes pairing` verifies pairs and `--write <note>` (or `--write --all`) records them; `notes validate` and archive sealing cover all three artifacts.
- Planning artifacts are complete bilingual triplets as well, enforced by `ai-workflow plan validate --plan <directory>` and recorded by `ai-workflow plan pairing --plan <directory>`. Every `spec.md`, `plan.md` and `tasks/task-NNN-slug.md` carries a `.zh.md` counterpart and a `.i18n.yaml` consistency record; the English side alone carries the YAML frontmatter, `REQ-###`/`AC-###` identifiers, counts and the `digest`, both sides mirror each other's structure, and only `task-NNN-slug.md` counts as a task document. The planning skill's numbered workflow writes all six files and treats `plan validate` as a hard completion gate, so `spec.md` or `plan.md` is never frozen without its `.zh.md` and `.i18n.yaml`. Explicit `--write` selections are fully pre-checked before any record is written and `--write --all` records only complete pairs. Existing single-language plans under `.ai-workflow/plans/` are not migrated, converted or exempted: they fail the new validation by design and stay byte-unchanged, so a plan frozen under the old single-language format is an expected legacy artifact rather than a new defect.
- The `output_language` feature was removed entirely: `config.yaml` carries only the optional `active_profile` field, install writes skills and role agents byte-for-byte from their templates with no injected prose-language directive, and a leftover `output_language` key is an unknown key that fails configuration validation before any write. Agent Notes and planning artifacts remain always-complete bilingual triplets, while structural elements, field names, fixed headings, `Status` and its values, file paths and dates remain English.
- Navigation JSON is authoritative and Markdown is generated from it.
- Coding creates no workflow manifest or run record other than the single implementation record at `<project>/.ai-workflow/plans/<planId>/implementation.yaml`, which holds `plan_id` with `status: in-progress` and an ISO 8601 `started_at` in the UTC+08:00 timezone before the first implementation step and after the final merge and owned cleanup becomes `status: completed` with an ISO 8601 `completed_at` in the UTC+08:00 timezone and the final commit SHA, except that a workspace root prefix delivery keeps the same record `in-progress` with `root_tasks_commit` until finalization; it is the only permitted run record. The record has only the two status values `in-progress` and `completed`.
- Host agent frontmatter stays host-native and is rendered from each template's `tools:` declaration: Codex uses TOML `model`/`model_reasoning_effort`, Claude uses `allowed-tools`, and OpenCode supports both `v1` (`mode: subagent` with singular `permission:` using `bash`/`task`) and `v2` (`mode: subagent` with ordered `permissions` rules using `shell`/`subagent`) selected by `--opencode-version v1|v2|auto` (`install`/`profile activate` default `auto` via `opencode --version`, library default `v2`), where the template `search` tool maps to `glob` plus `grep`, `web` maps to `webfetch` plus `websearch`, and every role denies nested dispatch (`task` in v1, `subagent` in v2) because only the primary orchestrator dispatches. OpenCode `hidden: true` removes an agent from the subagent catalog and blocks the `subagent` tool, so no dispatchable role may set it; that catalog requirement is guarded by `tests/behavior/opencode-agent-contract.test.ts`.
